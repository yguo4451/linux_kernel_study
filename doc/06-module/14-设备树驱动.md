# 34. 设备树驱动与 of_ 接口：从写死地址到读硬件说明书

> 阶段五第十四课。把驱动里硬编码的 `0x09000000` 换成从设备树动态读取，理解设备树驱动的完整模型：DTB → 内核扫描 → 匹配 compatible → 自动创建 device → probe。掌握 `of_` 接口和 `of_match_table` 机制，并分清"手动注册（模式 A）"与"设备树自动创建（模式 B）"两种模式。

## 一、为什么需要设备树

上一课写死：

```c
res[0].start = 0x09000000;   // 硬编码！换个板子就废了
```

真实系统里同一份驱动要跑在不同硬件上，UART 地址各不相同。地址不能写死在驱动里，应该写在一份"硬件说明书"里，驱动启动时去读。这份说明书就是**设备树（Device Tree）**，以 DTB 二进制形式由 bootloader/QEMU 传给内核。

## 二、设备树驱动模型

```
设备树 DTB（硬件说明书）
  ├─ pl011@9000000 { compatible = "arm,pl011"; reg = <0x09000000 0x1000>; }
  └─ ...（几百个节点）

内核启动
  → of_platform_populate() 扫描设备树
    → 为每个节点创建 platform_device（reg 自动填进 resource，节点挂到 of_node）
      → 匹配驱动的 of_match_table（比 compatible 字符串）
        → 匹配成功 → 自动 probe()
          → probe 里用 of_ 接口读属性 / devm_ioremap_resource
```

## 三、节点名：name vs full_name（本课踩坑）

设备树节点有**两个名字**：

```
name       = "pl011"              ← 节点名（不含单元地址）
full_name  = "/pl011@9000000"     ← 完整路径（名 + @ + 单元地址）
```

- `pl011@9000000` 是 **full_name**，`@9000000` 是单元地址（unit-address），用于同类设备去重
- `of_find_node_by_name(NULL, "pl011")` 匹配 **name**
- `of_find_node_by_path("/pl011@9000000")` 匹配 **full_name**

验证（QEMU 内）：

```sh
cat /proc/device-tree/pl011@9000000/name   # → pl011
ls -d /proc/device-tree/pl011@9000000      # → /proc/device-tree/pl011@9000000
```

## 四、of_ 接口（include/linux/of.h、of_address.h）

```c
of_find_node_by_path("/pl011@9000000");   // 按完整路径找节点
of_find_node_by_name(NULL, "pl011");      // 按 name 找节点
of_property_read_u32(np, "reg", &val);    // 读 u32 属性
of_address_to_resource(np, 0, &res);      // 读 reg 转成 resource（自动处理 #address-cells/#size-cells）
```

`of_address_to_resource` 会自动处理 `#address-cells`/`#size-cells`（arm64 都是 2），把 reg 转成 `resource`，不用自己解析。

## 五、of_match_table：驱动的 compatible 表

```c
static const struct of_device_id hello_of_match[] = {
    { .compatible = "arm,pl011", },
    { /* sentinel */ }                       // 必须空项结尾
};
MODULE_DEVICE_TABLE(of, hello_of_match);

static struct platform_driver hello_driver = {
    .driver = {
        .name = "hello_dt",
        .of_match_table = hello_of_match,    // 声明能处理哪些 compatible
    },
};
```

`MODULE_DEVICE_TABLE` 让 modprobe 能从模块文件读到 compatible 表，自动加载匹配的模块。

## 六、两种模式对比

| | 模式 A（手动注册） | 模式 B（设备树驱动） |
|---|---|---|
| device 谁创建 | 手动 `register_simple` | 内核扫描设备树自动创建 |
| device 有 of_node 吗 | ❌ 无 | ✅ 有 |
| 匹配依据 | `driver.name` 字符串 | `of_match_table` 的 compatible |
| 地址来源 | 手动填 / of_ 接口手动读 | 内核自动填进 resource |

本课实验是**混合体**：init 里 `of_find_node_by_path` 读地址 + 手动 `register_simple` 造 device。`of_match_table` 还没真正生效（device 没有 of_node）。

真正的模式 B：device 由设备树自动创建，`of_match_table` 的 compatible 匹配触发 probe。

## 七、实验：从设备树读 pl011 地址

```c
static int __init hello_plat_init(void) {
    struct device_node *np = of_find_node_by_path("/pl011@9000000");
    if (!np) {
        printk(KERN_ERR "no pl011 node\n");
        return -ENODEV;
    }

    if (of_address_to_resource(np, 0, res)) {
        printk(KERN_ERR "no reg\n");
        return -EINVAL;
    }

    printk(KERN_INFO "pl011 base=0x%llx size=0x%llx\n",
           (unsigned long long)res[0].start,
           (unsigned long long)resource_size(res));
    ...
}
```

验证输出：

```
pl011 base=0x9000000 size=0x1000     ← 和上一课写死的 0x09000000 一模一样
```

证明：**设备树就是硬件地址的来源**，上一课"手动填 0x09000000"本质是把设备树里的值抄了一遍。

## 八、要点回顾

```
设备树 DTB      ──硬件说明书──>  节点（name/full_name、compatible、reg）
of_ 接口        ──读属性──>  of_find_node_by_* / of_address_to_resource
of_match_table  ──compatible 匹配──>  自动创建 device → 自动 probe
模式 A          ──手动注册──>  driver.name 匹配，device 无 of_node
模式 B          ──设备树自动创建──>  compatible 匹配，device 有 of_node
```
