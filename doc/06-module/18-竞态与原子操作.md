# 38. 竞态与原子操作：atomic_t、spinlock 与 kthread

> 阶段五第十八课。用 4 个内核线程并发自增同一个变量，实测**裸 `++` 丢失更新**（400 万次丢 397 次），对比 `atomic_t` 和 `spinlock` 的正确性。顺带踩了两个 kthread 的坑（use-after-free、死等），最终用 completion 解决。这是内核同步的第一课。

## 一、竞态条件的本质

`x++` 看似一步，实际是三步：

```
① load  x 到寄存器
② 寄存器 +1
③ store 回内存
```

4 个 CPU 真并行时，两条执行的 ①②③ 交错，就会丢更新：

```
CPU0: load(5)                CPU1: load(5)
CPU0: add→6                       CPU1: add→6
CPU0: store(6)               CPU1: store(6)   ← 两次 +1 只留下一个 6
```

**这和业务层 C++ 多线程的竞态是同一个问题**，区别只是：内核是**多 CPU 真并行 + 中断随时打断**。

## 二、内核同步武器库

| 机制 | 场景 | 能睡眠 |
|---|---|---|
| `atomic_t` | 简单计数器 | — |
| `spinlock` | 短临界区、中断上下文 | ❌ |
| `mutex` | 长临界区、进程上下文 | ✅ |
| `rwlock` / `rwsem` | 读多写少 | rwlock❌ / rwsem✅ |
| `RCU` | 读极多写极少 | 读侧受限 |
| `completion` | 等事件完成 | ✅ |

## 三、实验：三种写法对比

```c
static int shared_plain;                        /* 裸 ++，竞态 */
static atomic_t shared_atomic = ATOMIC_INIT(0); /* 原子 */
static int shared_locked;                       /* spinlock 保护 */
static DEFINE_SPINLOCK(my_lock);

static int worker_fn(void *data)
{
	for (i = 0; i < ITERATIONS; i++) {
		shared_plain++;                 /* 竞态 */
		atomic_inc(&shared_atomic);     /* 原子 */
		spin_lock(&my_lock);            /* 加锁 */
		shared_locked++;
		spin_unlock(&my_lock);
	}
	...
}
```

4 个线程 × 100 万次，期望 400 万。

## 四、实测结果

```
hello_race: === start, expected = 4000000 ===
hello_race: plain  = 3999603  (lost 397)    ← 丢了 397 次！
hello_race: atomic = 4000000                ← 正确
hello_race: locked = 4000000                ← 正确
```

**裸 `++` 丢了 397 次**（400 万次里丢 0.01%），竞态窗口很窄但确实发生。`atomic_t` / `spinlock` 分毫不差。

## 五、atomic_t：LDXR/STXR 保证原子

```c
#include <linux/atomic.h>

atomic_t cnt = ATOMIC_INIT(0);
atomic_inc(&cnt);          /* 原子自增 */
int v = atomic_read(&cnt);
```

arm64 上 `atomic_inc` 编译成 **`LDXR`/`STXR`**（Load-Exclusive / Store-Exclusive）循环：

```
loop:
  LDXR  x0, [addr]     ; 独占读，同时标记该地址
  ADD   x0, x0, #1
  STXR  w1, x0, [addr] ; 独占写：如果期间有人动过该地址，写失败
  CBNZ  w1, loop       ; 失败就重试
```

`STXR` 失败（别的 CPU 抢先写了）就重试，保证 read-modify-write 整体原子。这就是无锁编程的地基（CAS 同源）。

## 六、spinlock：临界区串行

```c
#include <linux/spinlock.h>

static DEFINE_SPINLOCK(my_lock);

spin_lock(&my_lock);
/* 临界区：同一时刻只有一个 CPU 能进来 */
spin_unlock(&my_lock);
```

- 自旋等待（忙等），**不能睡眠**，可以在中断上下文用
- 临界区必须**极短**（只做几条指令），长时间持有会卡住其他 CPU

## 七、kthread 的两个坑（本次踩坑记录）

### 坑 1：kthread_stop 的 use-after-free

```
refcount_t: addition on 0; use-after-free.
  kthread_stop+0x16c
  hello_race_init
```

**原因**：worker `return 0` 后线程立即退出、`task_struct` 被回收；主线程之后 `kthread_stop(threads[i])` 访问的是野指针。

**kthread 契约**：线程要么活到被 `kthread_stop`，要么别保留 task_struct 指针去 stop。

### 坑 2：kthread_stop + msleep 死等

加 `while (!kthread_should_stop()) msleep(50);` 后，模块卡在 `Loading`，`insmod` 永不返回。

### 最终方案：completion（更简单可靠）

```c
static struct completion all_done;
static atomic_t finished = ATOMIC_INIT(0);

/* worker 尾部 */
if (atomic_inc_return(&finished) == NR_THREADS)
    complete(&all_done);
return 0;       /* 直接退出，task_struct 自动回收 */

/* init */
init_completion(&all_done);
atomic_set(&finished, 0);
for (i = 0; i < NR_THREADS; i++)
    kthread_run(worker_fn, (void *)(long)i, "race_worker%d", i);
wait_for_completion(&all_done);    /* 等所有 worker 完成 */
```

**经验**：只想"等所有线程跑完"时，用 completion 比 kthread_stop 省心得多。

## 八、要点回顾

```
竞态       ──load/add/store 非原子 + 多核并行──> 丢更新（实测丢 397 次）
atomic_t   ──LDXR/STXR 独占读写循环──> 单变量原子操作
spinlock   ──自旋 + 临界区串行──> 保护多步操作，不能睡眠
mutex      ──睡眠等待──> 长临界区、进程上下文
kthread    ──return 后线程即退出──> 别拿 task_struct 去 kthread_stop
completion ──等事件完成──> 比 kthread_stop 更适合"等线程跑完"
```
