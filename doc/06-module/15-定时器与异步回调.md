# 35. 定时器与异步回调：timer_list 与 hrtimer

> 阶段五第十五课。用 `timer_list` 实现"注册回调 → 异步触发 → 循环定时"，理解异步回调机制和软中断上下文限制；通过实测 jiffies 间隔反推 HZ，挖出 timer wheel 的精度损失，并对比高精度定时器 hrtimer。这是真实硬件中断（request_irq）的最佳前奏。

## 一、为什么要异步

之前所有实验都是**轮询**（poll）：

```c
while (!has_data)  wait_event(...);   // 一直等
```

真实系统用**异步回调**：

```
事件发生 → 内核自动调用你注册的函数 → 处理完返回
```

定时器是最简单的异步模型：你登记"1 秒后叫我"，然后继续干别的，时间到内核自动回调。

## 二、timer_list 三件套

```c
#include <linux/timer.h>

static struct timer_list my_timer;

static void timer_callback(struct timer_list *t)
{
    /* 软中断上下文，不能睡眠！ */
    mod_timer(&my_timer, jiffies + msecs_to_jiffies(1000));  // 重新定时
}

/* init */
timer_setup(&my_timer, timer_callback, 0);                   // 注册回调
mod_timer(&my_timer, jiffies + msecs_to_jiffies(1000));      // 定时 1 秒

/* exit */
del_timer_sync(&my_timer);                                   // 同步删除
```

| API | 作用 |
|---|---|
| `timer_setup` | 绑定回调函数 |
| `mod_timer` | 设定/修改到期时间（jiffies 绝对时间） |
| `del_timer_sync` | 删除定时器，**等待正在执行的回调结束** |

## 三、软中断上下文：不能睡眠

`timer_callback` 运行在**软中断上下文**（softirq），和硬中断一样受限：

- ❌ 不能睡眠（`msleep`、`copy_to_user`、`kmalloc(GFP_KERNEL)` 都不行）
- ✅ 要快，尽快返回
- 需要睡眠的工作 → 用 workqueue（进程上下文）

## 四、实测数据：反推 HZ 与精度损失

实验输出：

```
hello_timer: armed, tick in 1s
hello_timer: tick #1 (jiffies=4295013616)   时间戳 485.283561
hello_timer: tick #2 (jiffies=4295013872)   时间戳 486.307564
...
hello_timer: bye, total=10
```

**反推 HZ**：

```
jiffies 间隔 = 4295013872 - 4295013616 = 256
时间戳间隔  = 486.307564 - 485.283561  = 1.024 秒
HZ = 256 / 1.024 = 250          → CONFIG_HZ = 250
```

**关键发现**：`msecs_to_jiffies(1000)` 在 HZ=250 下 = 250 jiffies = 1.000 秒，但实测间隔是 **256 jiffies = 1.024 秒**，多了 6 ticks（24ms），且是**稳定的系统性偏差**。

## 五、精度损失的根源：timer wheel

```
timer wheel 分层（kernel/time/timer.c）：
  LVL0: 0~63 jiffies，粒度 1 tick
  LVL1: 64~511 jiffies，粒度 8 ticks    ← 250 jiffies 落在这里
  LVL2: 512~4095，粒度 64 ticks
  ...

250 jiffies 的定时器加入 LVL1 → 实际延迟 0~7 ticks（8 的整数倍）
实测延迟 6 ticks → 256 jiffies = 1.024 秒
```

**结论**：`timer_list` 不是高精度定时器，它受时间轮粒度约束，实际间隔 = 设定值 + 0~粒度 的偏差。

## 六、高精度定时器：hrtimer

需要精确间隔时用 `hrtimer`（基于纳秒级时钟源，红黑树管理）：

```c
#include <linux/hrtimer.h>
#include <linux/ktime.h>

static struct hrtimer my_hrtimer;

static enum hrtimer_restart hrtimer_callback(struct hrtimer *t)
{
    hrtimer_forward_now(t, ms_to_ktime(1000));   // 重新定时 1000ms
    return HRTIMER_RESTART;
}

/* init */
hrtimer_init(&my_hrtimer, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
my_hrtimer.function = hrtimer_callback;
hrtimer_start(&my_hrtimer, ms_to_ktime(1000), HRTIMER_MODE_REL);

/* exit */
hrtimer_cancel(&my_hrtimer);
```

| | `timer_list` | `hrtimer` |
|---|---|---|
| 精度 | jiffies 粒度（ms~几十 ms） | 纳秒级 |
| 实现 | 时间轮 timer wheel | 红黑树 + 高精度时钟源 |
| 实测 | 1.024 秒（多 24ms） | ~1.000 秒 |
| 用途 | 粗粒度定时、心跳、看门狗 | 实时任务、精确延时（cyclictest） |

## 七、实测对比：精度差 1000 倍

hrtimer 用 `ktime_get()` 测纳秒级间隔，实测输出：

```
timer_list（上一课）：
  tick #1 → #2: 1024 ms           ← 系统性偏差 +24ms

hrtimer（本课）：
  tick #1: 1000.024 ms
  tick #2:  999.994 ms
  tick #3: 1000.001 ms
  tick #5:  999.985 ms
  范围: 999.985 ~ 1000.024 ms     ← 偏差 -15 ~ +24 微秒
```

| | timer_list | hrtimer | 提升 |
|---|---|---|---|
| 实测间隔 | 1024 ms | 1000 ± 0.025 ms | — |
| 偏差 | **+24 ms**（系统性） | **±0.025 ms**（随机抖动） | **约 1000 倍** |
| 偏差性质 | 固定偏大（时间轮粒度） | 有正有负（随机抖动） | — |

**两种偏差本质不同**：

- timer_list 的 +24ms 是**系统性**的：每次都被 timer wheel 的桶边界"卡住"，固定迟到
- hrtimer 的 ±25 微秒是**随机抖动**：有迟到也有早到，来源是中断响应延迟、系统负载、微架构因素

**实时意义**：汽车 ECU 要求"每 1ms 执行一次"，timer_list 稳定迟到 24ms 会直接搞乱控制周期，hrtimer 的 ±25 微秒才是可接受精度。cyclictest 内部就用 hrtimer——本实验本质是手写了一个迷你 cyclictest。

```
普通内核：±25 微秒抖动（空闲）
PREEMPT_RT：可压到 ±5 微秒以内（硬实时）
```

## 八、和硬件中断的对应关系

定时器把中断的结构提前演练了一遍：

```
timer_setup    ≈ request_irq     注册回调
时间到触发      ≈ 硬件中断到来     异步触发
回调函数        ≈ 中断处理函数     上下文受限，不能睡眠
del_timer_sync ≈ free_irq        同步注销
```

先跑通定时器（不用处理 IRQ 号、共享、触发类型），再上真实硬件中断。
