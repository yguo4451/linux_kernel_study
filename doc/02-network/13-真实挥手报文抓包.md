# 18. 真实挥手报文：tcpdump 抓包实证

> 网络子系统实证篇。用刚集成的 tcpdump 抓 loopback 上的 TCP 关闭过程，把 doc/15 的四次挥手理论落到真实报文。

## 实验环境与命令

- 内核 6.6.44 + BusyBox 1.36.1 + 静态 tcpdump 4.99.4（见 doc/16）
- 抓包接口 `lo`（loopback），端口 12345
- 关键：两个 `nc` 都套 `timeout` 兜底，避免 BusyBox nc 读 EOF 后挂住不退出

```sh
tcpdump -i lo -l -n -S -tttt 'tcp port 12345' > /tmp/fin.log 2>&1 &
sleep 1
timeout 8 nc -l -p 12345 > /dev/null &      # server：8 秒后被杀 → close
sleep 1
printf 'hello' | timeout 2 nc 127.0.0.1 12345   # client：发完数据后被杀 → close
sleep 9
pkill tcpdump; cat /tmp/fin.log
```

## 完整报文序列（`-S` 绝对序号）

| # | Flags | seq / ack | 含义 |
|---|-------|-----------|------|
| 1 | `[S]` | seq 684655520 | 握手 ① SYN |
| 2 | `[S.]` | ack 684655521 | 握手 ② SYN+ACK |
| 3 | `[.]` | ack 2208572102 | 握手 ③ ACK |
| 4 | `[P.]` | seq 684655521:684655526, len 5 | 数据 `hello` |
| 5 | `[.]` | ack 684655526 | 确认数据 |
| 6 | `[F.]` | seq 684655526 | 挥手 ① client 发 FIN |
| 7 | `[F.]` | seq 2208572102, ack 684655527 | 挥手 ② server 发 FIN+ACK（**合并**）|
| 8 | `[.]` | ack 2208572103 | 挥手 ③ client 发 ACK |

## 核心发现：四次挥手退化成三次

本次挥手只有 3 个报文（6、7、8）。标准"四次挥手"里的「② ACK」和「③ FIN」**合并成了一个 `[F.]`**。

```
标准四次（被动方还有数据处理）        本次（被动方立即 close）
──────────────────────────          ──────────────────────────
① A ──FIN──▶ B                       ① client ──FIN──▶ server
② A ◀─ACK── B                        ② server ──FIN+ACK──▶ client
③ A ◀─FIN── B                        ③ client ──ACK──▶ server
④ A ──ACK──▶ B
```

**合并条件**：被动方收到 FIN 时应用立刻 `close()`，且发送队列空、接收缓冲无未读数据，TCP 就在同一报文同时置 `FIN|ACK`。

## 序列号验证（严丝合缝）

- client FIN `seq 684655526`：数据 `hello` 占 `684655521..684655525`，FIN 紧跟其后 ✅
- server FIN+ACK `ack 684655527` = client FIN seq + 1 ✅
- client 最后 ACK `ack 2208572103` = server FIN seq + 1 ✅

FIN 和 SYN 一样**消耗一个序号**，这是抓包里最容易看明白的"TCP 序号"教学点。

## 源码呼应（doc/15 结论）

`tcp_close()`（`net/ipv4/tcp.c`）在应用 `close()` 时被调用：

- 若发送队列有未发数据 → 先发完，再置 FIN；
- 若接收队列有未读数据 → 先回 ACK，随后 FIN；
- 若两边都空 → 直接发 `FIN`（本次实验的情况），于是 ACK 与 FIN 合并成 `[F.]`。

这正是"四次"变"三次"的内核实现原因。

## 对比实验：标准四次挥手（python 延迟 close）

要抓到"真四次挥手"，必须让被动方收到 FIN 后**延迟 close**。`nc` 是双向管道，读到 socket EOF 就退出，天然"立即关"，抓不到；改用宿主机 python server 精确控制 close 时机。

宿主机 `scripts/tcp_fin_server.py`（关键就两行）：

```python
data = conn.recv(1024)   # 收到 client 数据 + FIN，应用不 close
time.sleep(3)            # 拖 3 秒，内核先自动回 ACK
conn.close()             # 现在才 close -> 发 FIN
```

guest 内抓 eth0（连宿主机 `10.0.2.2`）：

```sh
tcpdump -i eth0 -l -n -S 'tcp port 12346' > /tmp/fin4.log 2>&1 &
sleep 1
printf 'hello' | timeout 2 nc 10.0.2.2 12346
sleep 6; pkill tcpdump; cat /tmp/fin4.log
```

### 抓到的四次挥手（ACK 与 FIN 分开 3 秒）

| # | Flags | 时间 | 含义 |
|---|-------|------|------|
| 6 | `[F.]` seq 1289907385 | .828 | ① client FIN |
| 7 | `[.]` ack 1289907386 | .828 | ② 单独 ACK（应用未 close）|
| 8 | `[F.]` seq 64002 | 57.831 | ③ server FIN（**3.003 秒后**）|
| 9 | `[.]` ack 64003 | .832 | ④ client ACK |

报文 7 是纯 `[.]`（无 F 标志），报文 8 才是 `[F.]`——这是"四次挥手"与"三次挥手"的唯一肉眼区别。3.003 秒 = `time.sleep(3)`，期间 socket 仍 open，内核已自动回 ACK。

### 结论

**"三次"还是"四次"，取决于被动方应用收到 FIN 后多久 `close()`**：

- 立即 close → ACK 与 FIN 合并 → 三次
- 延迟 close → 内核先回 ACK，应用 close 时才发 FIN → 四次

`tcp_close()` 的"发送队列空就发 FIN"逻辑不变，变的只是应用层 close 的早晚。

## 分界阈值：40ms 的 delayed ACK

"三次还是四次"没有"延迟几秒"的固定阈值，而是**两个事件的赛跑**：

- 事件①：延迟 ACK 定时器到期（~40ms，最长 200ms）
- 事件②：应用 `close()`

```
② 先于 ① → ACK 未发 → FIN 捎带 ACK → 三次挥手
① 先于 ② → ACK 已发 → FIN 单独走 → 四次挥手
```

### 源码链路

```
收到 FIN → tcp_fin()                       net/ipv4/tcp_input.c:4417
             inet_csk_schedule_ack()        只打标记，不立即发
             inet_csk_enter_pingpong_mode() 延迟上限放宽到 200ms
         → __tcp_ack_snd_check()           tcp_input.c:5592
             ├─ quickack/ICSK_ACK_NOW/满帧 → 立即 ACK
             └─ 否则 → tcp_send_delayed_ack()  tcp_output.c:4026
                         delay = ato（初始 40ms），上限 200ms
```

### 具体数值（真实时间，与 HZ 无关）

| 宏 | 定义 | 值 |
|----|------|-----|
| `TCP_DELACK_MIN` | `HZ/25` | 40ms |
| `TCP_DELACK_MAX` | `HZ/5` | 200ms |
| `TCP_ATO_MIN` | `HZ/25` | 40ms（ato 初始值）|

`include/net/tcp.h:133,135`。`HZ/25`、`HZ/5` 的写法保证 `HZ=250` 与 `HZ=1000` 下真实时间都恒为 40ms / 200ms。6.6 新增 sysctl `net.ipv4.tcp_delack_max`（默认 200ms）。

### 用自己的实验反证

- 实验 A：FIN→FIN+ACK 间隔 3ms **< 40ms** → 三次 ✅
- 实验 B：FIN→ACK→FIN 间隔 3 秒 **> 40ms** → 四次 ✅

注意：实验 B 的 server 在 macOS，ACK 立即回；纯 Linux 两端才会真正走 40ms 延迟路径。40ms 是 Linux 实现，非 TCP 协议规定。

## 陷阱

- **BusyBox nc 会挂住**：client 模式读完 stdin EOF 后不一定退出，`nc` 卡住会让后续命令排队，必须套 `timeout` 或 `pkill`。
- **loopback 也要 `-i lo`**：走 `127.0.0.1` 不经过 eth0，宿主机 filter-dump 抓不到，必须 guest 内 `tcpdump -i lo`。
- **`-S` 必加**：tcpdump 默认把序号显示成相对值，`-S` 显示绝对序号，才能看出 FIN 的 seq 恰好在数据之后。
- **RST 替代 FIN**：若关闭时接收缓冲还有未读数据，内核会发 `[R]` 而非 `[F]`，挥手直接变成单报文 RST。
