# 13 数据发送路径：tcp_sendmsg → tcp_write_xmit

> 对应源码：`net/ipv4/tcp.c`（`tcp_sendmsg`）、`net/ipv4/tcp_output.c`（`tcp_write_xmit`）、`include/net/tcp.h`（cwnd 访问器）。
> 前置知识：doc/09（快速路径）、doc/10~12（拥塞控制）。

## 核心洞察：cwnd 的一写一读

TCP 拥塞控制是一个闭环，关键字段 `tp->snd_cwnd` 有两个操作者：

- **收包侧（tcp_input.c）写**：`tcp_ack → tcp_cong_control → tcp_cong_avoid` 里调用 `tcp_snd_cwnd_set()` 放大 cwnd；丢包/RTO 时调用 `tcp_snd_cwnd_set()` 砍小 cwnd。
- **发包侧（tcp_output.c）读**：`tcp_write_xmit → tcp_cwnd_test` 里用 `tcp_snd_cwnd()` 读取 cwnd 来限制发送速率。

访问器定义在 `include/net/tcp.h:1228-1235`：

```c
static inline u32 tcp_snd_cwnd(const struct tcp_sock *tp)
{
	return tp->snd_cwnd;
}

static inline void tcp_snd_cwnd_set(struct tcp_sock *tp, u32 val)
{
	WARN_ON_ONCE((int)val <= 0);
	tp->snd_cwnd = val;
}
```

> `tcp_snd_cwnd_set` 里的 `WARN_ON_ONCE((int)val <= 0)` 是防御性断言：cwnd 绝不能为 0 或负数，否则发送路径会彻底卡死。

典型"写"场景——RTO 超时进入 Loss 状态（`tcp_input.c:2675`）：

```c
/* tcp_enter_loss() 内 */
tcp_snd_cwnd_set(tp, tcp_packets_in_flight(tp) + 1);
```

超时说明网络彻底拥塞，cwnd 被猛砍到"在途包 + 1"，只允许再发 1 个探测包。

## 发送路径调用链

```
用户态 write()/send()
      │
      ▼
tcp_sendmsg()            tcp.c:1339    加锁 sock → tcp_sendmsg_locked
      │
      ▼
tcp_sendmsg_locked()     tcp.c:1038    用户数据 → skb，挂 write_queue（不发）
      │
      ▼
tcp_push()                            决定"现在发还是攒着"
      │
      ▼
__tcp_push_pending_frames()  tcp_output.c:2937
      │
      ▼
tcp_write_xmit()         tcp_output.c:2670   ★ 发送核心：五道闸门
      │
      ▼
tcp_transmit_skb()                    封装 TCP 头 → IP 层 → 网卡
```

## 一、tcp_sendmsg_locked（tcp.c:1038）

职责：**只入队，不发送**。

- `tcp_send_mss()` 计算 MSS 和 `size_goal`（一个 skb 最多装多少）
- `while (msg_data_left(msg))` 循环里：
  - `tcp_write_queue_tail()` 取队尾 skb，能合并就追加数据
  - 否则 `new_segment`：`sk_stream_memory_free` 检查内存 → `tcp_stream_alloc_skb` 分配 → `tcp_skb_entail` 挂到 write_queue
  - 数据拷贝进 skb 后，推进 `tp->write_seq` 和 `TCP_SKB_CB(skb)->end_seq`
- 循环结束/空间不足时调 `tcp_push()` 触发真正发送

**设计意图**：应用多次小 write，内核攒成大包（配合 TSO）一次发出，降低 per-packet 开销。这也是为什么"write 返回了 ≠ 数据已上网络"。

## 二、tcp_write_xmit（tcp_output.c:2670）

发送核心，`while ((skb = tcp_send_head(sk)))` 逐包放行，每包过五道闸门：

```
for each skb in write_queue:
  ① tcp_pacing_check       → pacing 限速没到发送时刻？break
  ② tcp_cwnd_test          → 拥塞窗口满？break           ← 读 cwnd
  ③ tcp_snd_wnd_test       → 对端 rwnd 满？break
  ④ tcp_nagle_test         → Nagle 说"再等等"？break
  ⑤ tcp_small_queue_check  → TSQ 本地排队太多？break
        │ 全通过
        ▼
  tcp_transmit_skb()  → 真正发送
```

### 闸门② tcp_cwnd_test（tcp_output.c:2044）

```c
static inline unsigned int tcp_cwnd_test(const struct tcp_sock *tp,
					 const struct sk_buff *skb)
{
	u32 in_flight, cwnd, halfcwnd;

	/* 最后的 FIN 不受 cwnd 限制 */
	if ((TCP_SKB_CB(skb)->tcp_flags & TCPHDR_FIN) &&
	    tcp_skb_pcount(skb) == 1)
		return 1;

	in_flight = tcp_packets_in_flight(tp);
	cwnd = tcp_snd_cwnd(tp);
	if (in_flight >= cwnd)
		return 0;                        /* 在途已满，不发 */

	halfcwnd = max(cwnd >> 1, 1U);
	return min(halfcwnd, cwnd - in_flight); /* 最多放行 min(cwnd/2, 剩余) */
}
```

其中在途包计数（`include/net/tcp.h:1216`）：

```c
static inline unsigned int tcp_packets_in_flight(const struct tcp_sock *tp)
{
	return tp->packets_out - tcp_left_out(tp) + tp->retrans_out;
}
/* tcp_left_out = sacked_out + lost_out */
```

**为什么 `min(halfcwnd, cwnd - in_flight)`？** 保留半窗口余量，避免一次 ACK 风暴把整个 cwnd 一口气打满，让 cwnd 的锯齿曲线更平滑。这是 Linux 对纯 AIMD 的工程改进。

### 闸门④ Nagle（tcp_output.c:1954）

```c
static bool tcp_nagle_check(bool partial, const struct tcp_sock *tp,
			    int nonagle)
{
	return partial &&
		((nonagle & TCP_NAGLE_CORK) ||
		 (!nonagle && tp->packets_out && tcp_minshall_check(tp)));
}
```

- `partial`：该包不满一个 MSS
- `TCP_NAGLE_CORK`：应用设置了 `TCP_CORK`（显式攒数据）
- `!nonagle && packets_out && minshall`：默认情况下，只要还有未确认数据在途、且之前发过未确认的小包，就**不发这个小包**

一句话：**有在途未确认数据时，不发不满 MSS 的小包**。Minshall 修改版（`tcp_minshall_check`，tcp_output.c:1926）进一步要求"之前的小包也被确认了"才发。

### 闸门⑤ TSQ（tcp_output.c:2568）

`tcp_small_queue_check` 限制"网卡尚未确认的本地排队字节"不超过 `min(2×skb_truesize, 速率窗口)`，防止高 BDP 连接把内存全塞进设备队列。

- 本质是**本地资源/延迟控制**，不是拥塞控制
- 好处：降低 bufferbloat（缓存膨胀）带来的排队延迟
- 触发后设 `TSQ_THROTTLED`，等 TX 完成回调再唤醒发送

## 三、发完记账与 ACK 时钟

`tcp_write_xmit` 尾部：

```c
is_cwnd_limited |= (tcp_packets_in_flight(tp) >= tcp_snd_cwnd(tp));
if (likely(sent_pkts || is_cwnd_limited))
	tcp_cwnd_validate(sk, is_cwnd_limited);
```

发完后若"在途包已达 cwnd"，标记 `is_cwnd_limited`。之后只有等 ACK 回来（收包侧）通过 `tcp_snd_cwnd_set` 放大 cwnd，发送侧才有新额度——**这就是 ACK 时钟驱动的本质**：ACK 回来一次，cwnd 涨一点，发送才有油。

## 四、闭环全景

```
        ┌─────────────────────────────────────────────────────┐
        │                 ACK 路径（tcp_input.c）              │
        │  tcp_ack → tcp_cong_control → tcp_cong_avoid        │
        │            └─ tcp_snd_cwnd_set(tp, ...)  ← 写       │
        └───────────────────────┬─────────────────────────────┘
                                │ 同一个 tp->snd_cwnd
        ┌───────────────────────▼─────────────────────────────┐
        │               发送路径（tcp_output.c）               │
        │  tcp_sendmsg → tcp_write_xmit → tcp_cwnd_test       │
        │            └─ tcp_snd_cwnd(tp)  ← 读，限速          │
        └─────────────────────────────────────────────────────┘
```

## 六、陷阱

1. **write 返回 ≠ 已发送**：数据可能还在 write_queue 里等 cwnd/rwnd 额度，或等 Nagle。
2. **cwnd 为 0 是死局**：`tcp_snd_cwnd_set` 的 `WARN_ON_ONCE` 就是在防御这种状态——发送侧读不到额度会永久阻塞。
3. **Nagle 与延迟**：交互式小包应用必须 `TCP_NODELAY`，否则每个小包最多等一个 RTT。
4. **TSQ 不是拥塞控制**：它限制的是本地设备队列，不影响 cwnd 数值，但会影响实际发送节奏。

## 七、实验验证：loopback 传 2MB（QEMU 实测）

环境：QEMU 内 BusyBox，`dd` 生成 2MB 文件，`nc` loopback 传输，读 `/proc/net/snmp` + `/proc/net/netstat` 原始计数。

### 实测数据（前 → 后）

| 计数器 | 前 | 后 | Δ |
|--------|----|----|----|
| TCPOrigDataSent | 151 | 280 | +129 |
| TCPDelivered | 157 | 287 | +130 |
| TCPPureAcks | 117 | 221 | +104 |
| OutSegs | 289 | 524 | +235 |
| RetransSegs | 1 | 1 | 0 |
| TCPFastRetrans | 0 | 0 | 0 |
| TCPTimeouts | 0 | 0 | 0 |
| TCPHPHits | 0 | 0 | 0 |

### 结论

1. **TSO/GSO 打包**：2MB 仅 129 个数据段（每段 ~16384B = 2¹⁴），而非 1448 个单 MSS 段。对应 `tcp_write_xmit` 里 `tcp_tso_segs`/`tcp_mss_split_point` 把多 MSS 打包进一个 skb。
2. **发送≈确认**：`TCPOrigDataSent +129` ≈ `TCPDelivered +130`，cwnd 全程放行，ACK 时钟闭环正常。
3. **零丢包**：`RetransSegs`/`TCPFastRetrans`/`TCPTimeouts` 全 0，cwnd 只涨不砍。
4. **数字对账**：`OutSegs +235 = 数据 129 + ACK 104`（+握手），`TCPPureAcks +104` 正是服务端回的纯 ACK。
5. **快路径未命中**：`TCPHPHits = 0`，因 loopback+GRO 合并出大 truesize 的 skb，触发 `tcp_rcv_established` 中 `skb->truesize > sk->sk_forward_alloc` 落入慢路径。印证 doc/09：快路径进入条件严格，skb 形态非常规即退回慢路径。
