# 页表与虚拟地址空间：MMU 的翻译机制

> 内存管理子系列第 3 篇。前两篇都是物理内存（Buddy 管页、SLUB 管对象），本篇回答**虚拟地址怎么翻译成物理地址**——这是缺页异常（模块 4）的最后一块地基。

## 一、为什么需要虚拟地址

用户程序看到的是**虚拟地址**，CPU 实际访问内存用的是**物理地址**，中间由 **MMU（Memory Management Unit）** 翻译。三个理由：

1. **隔离**：每个进程有独立的虚拟地址空间，A 进程碰不到 B 进程的内存
2. **保护**：页表项里带权限位，越权访问（写只读页、用户态访问内核页）立刻被 MMU 拦下
3. **连续假象**：进程看到的是一大块连续地址，物理上可以散落各处

```
虚拟地址 VA ──MMU──▶ 物理地址 PA
   │                    │
   │ 查页表              │ 真实内存
   ▼                    ▼
 0x00400000         0x41a3f000（任意散落的页）
```

## 二、多级页表：为什么不用一张大表

如果虚拟地址直接查一张大表，4KB 页、52 位 VA 需要 $2^{40}$ 个页表项——天文数字，根本存不下。

**解法：分级**。把虚拟地址切成几段，每段查一级页表，逐级定位：

```
虚拟地址（52 bit，4KB 页）
┌────┬─────┬─────┬─────┬─────┬────────────┐
│PGD │ P4D │ PUD │ PMD │ PTE │ 页内偏移    │
│4bit│ 9bit│ 9bit│ 9bit│ 9bit│ 12bit      │
└────┴─────┴─────┴─────┴─────┴────────────┘
 51:48 47:39 38:30 29:21 20:12  11:0
```

**我们的内核是 5 级页表**（`CONFIG_PGTABLE_LEVELS=5`，52 位 VA + 4KB 页）：

```
mm->pgd（每进程一个 PGD，只有 16 项）
  → P4D（512 项）
    → PUD（512 项）
      → PMD（512 项）
        → PTE（512 项）→ 指向真正的物理页
```

**翻译过程**：

1. CPU 从 `TTBR0_EL1` 寄存器读 PGD 基址（进程切换时写入）
2. 用 VA 的 [51:48] 选 PGD 项 → 得到 P4D 表地址
3. 用 [47:39] 选 P4D 项 → PUD 表地址
4. 依次类推，最后 PTE 项给出物理页号
5. 物理页号 + 页内偏移 [11:0] = 最终物理地址

> **为什么分级反而省内存**：大多数进程只用到地址空间的一小部分，没用的中间级页表**根本不用建**。一张大表则必须全建。

## 三、页表项 PTE 的位（arm64）

```c
// arch/arm64/include/asm/pgtable-hwdef.h:156
#define PTE_VALID   (1 << 0)   // 有效位：0 = 该页不存在（→ 缺页！）
#define PTE_TYPE_PAGE (3 << 0)
#define PTE_USER    (1 << 6)   // AP[1]：用户态可访问
#define PTE_RDONLY  (1 << 7)   // AP[2]：只读
#define PTE_SHARED  (3 << 8)   // 缓存共享属性
#define PTE_AF      (1 << 10)  // Access Flag：硬件访问后自动置位
#define PTE_NG      (1 << 11)  // non-Global：进程私有，不跨进程复用
#define PTE_DBM     (1 << 51)  // 脏位管理
#define PTE_PXN     (1 << 53)  // 特权态不可执行
#define PTE_UXN     (1 << 54)  // 用户态不可执行
#define PTE_ATTRINDX(t) ((t) << 2)  // 内存属性（缓存策略）
```

**重点位**：

- `PTE_VALID=0` → 页不存在 → **访问它触发缺页异常**（模块 4 的主角）
- `PTE_USER` / `PTE_RDONLY` / `PTE_UXN` → 权限位，越权触发**权限故障**（段错误 segfault 的来源）
- `PTE_AF` → 访问标志，硬件访问后自动置 1，内核据此做 LRU 老化（模块 5 回收要用）

## 四、进程地址空间：mm_struct + VMA

页表是"翻译工具"，但进程的**内存布局**由 `mm_struct` + `vm_area_struct` 描述：

```c
// include/linux/mm_types.h:835
struct mm_struct {
	struct maple_tree mm_mt;   // 所有 VMA 的树（按地址排序）
	unsigned long mmap_base;   // mmap 区域基址
	unsigned long task_size;   // 用户空间大小
	pgd_t *pgd;                // ★ 页表根（PGD），进程切换时装入 TTBR0
	atomic_t mm_users;         // 引用计数
};

// include/linux/mm_types.h:712
struct vm_area_struct {       // 一个 VMA = 一段连续的虚拟地址区域
	unsigned long vm_start;   // [vm_start, vm_end) 区域范围
	unsigned long vm_end;
	struct mm_struct *vm_mm;  // 属于哪个进程
	pgprot_t vm_page_prot;    // 访问权限
	vm_flags_t vm_flags;      // READ/WRITE/EXEC/SHARED/PRIVATE...
};
```

**VMA 和页表的区别**（重要）：

- **VMA**：描述"这段虚拟地址**应该**有什么属性"（可读？可写？是文件映射还是匿名？）——**软件层**的数据结构
- **页表**：描述"这段虚拟地址**实际**映射到哪个物理页"——**硬件**翻译用的数据结构

缺页异常（模块 4）就是两者的配合：访问一个 VA → 页表里没有（`PTE_VALID=0`）→ 内核查 VMA 确认"这个访问合法" → 分配物理页 + 填页表项。

## 五、TLB：页表的缓存

每次访问内存都查 4~5 级页表太慢（一次访问要 5 次内存读取）。**TLB（Translation Lookaside Buffer）** 是 MMU 里的硬件缓存，缓存"虚拟页号 → 物理页号"的映射。

```
CPU 访问 VA
  → 查 TLB（1 个时钟周期，快）
      ├─ 命中 → 直接用物理地址
      └─ 未命中 → 硬件走页表（慢，5 次内存访问）→ 结果填回 TLB
```

- 进程切换要**刷 TLB**（否则 A 进程会读到 B 进程的映射）——arm64 用 ASID（地址空间 ID）避免频繁全刷
- `PTE_NG` 位标记"非全局"页，进程切换时这些 TLB 项作废

## 六、动手实验（QEMU 内）

### 实验 1：看进程的虚拟地址空间

```sh
cat /proc/self/maps
# 00400000-0041d000 r-xp ... /bin/busybox    ← 代码段（可读可执行）
# 00bdd000-00bde000 rw-p ... [stack]          ← 栈
# 每一行是一个 VMA！
```

每一行就是一个 `vm_area_struct`：

| 列 | 含义 |
|----|------|
| `00400000-0041d000` | `vm_start - vm_end`（虚拟地址范围）|
| `r-xp` | 权限：读/执行/私有 |
| `/bin/busybox` | 映射来源（文件 or `[heap]`/`[stack]`/`[anon]`）|

### 实验 2：看共享库/堆/栈的典型布局

```sh
cat /proc/1/maps | grep -E "heap|stack|ld-|libc"
# 观察 [heap] 在低地址、[stack] 在高地址、共享库在中间
```

### 实验 3：确认 52 位地址空间的"空旷"

```sh
cat /proc/self/maps | head
# 地址都是 0x0000_0040_0000 这种低位地址，整个 2^51 的用户空间只用了一丁点
```
