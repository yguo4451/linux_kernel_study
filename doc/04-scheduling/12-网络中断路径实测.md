# 12 网络中断路径实测（ping 实验）

## 目标

用一次 ping 实测，把"硬中断 → softirq → 网络协议栈"的完整链路打通，并揭示网络栈"收包异步、发包同步"的根本设计差异。

## 实验方法

在 QEMU guest 里采样前后对比：

```sh
# ping 前
cat /proc/interrupts | grep virtio
cat /proc/softirqs | grep -E "NET_TX|NET_RX"
# 制造流量
ping -c 200 -i 0.05 10.0.2.2 > /dev/null
# ping 后
cat /proc/interrupts | grep virtio
cat /proc/softirqs | grep -E "NET_TX|NET_RX"
```

## 实测结果

| 指标 | ping 前 | ping 后 | 增量 |
|------|---------|---------|------|
| `virtio0-input.0` (irq 17) | 2 | 297 | +295 |
| `virtio0-output.0` (irq 18) | 2 | 297 | +295 |
| `NET_RX` softirq | 2 | 297 | +295 |
| `NET_TX` softirq | 1 | 1 | **+0** |

## 核心发现：NET_TX 为什么不涨

发 200 个包，`NET_TX` softirq 一次没涨——这是网络栈的根本设计：

- **接收是异步的**：数据到达是硬件事件（中断），无法预知。中断只做最少的事，真正的收包处理（协议栈解析、socket 唤醒）丢给 `NET_RX` softirq。
- **发送是同步的**：应用主动调用 `send()`，协议栈直接构建 skb → 直接调驱动 `ndo_start_xmit` → 一步到位，无需 softirq 延迟处理。

所以 `NET_TX` softirq 在现代内核几乎闲置（历史上用于发送完成清理，现被 NAPI 替代）。

## 一次 ping 的完整中断旅程

```
【发包路径】同步，不走 softirq
ping 进程 → 协议栈 → virtio ndo_start_xmit → 发送队列 → kick 设备
         ↓ 设备发完
   output 中断(18) → 驱动释放 skb（发送完成清理）

【收包路径】异步，走 softirq
设备收到 reply → 接收队列
         ↓
   input 中断(17) → irq/17 线程 → raise NET_RX_SOFTIRQ
         ↓
   ksoftirqd 处理 NET_RX → 协议栈解析 → 唤醒 ping 进程
```

## 关键结论

1. **中断计数增量 = 网络事件次数**：每个收/发包触发一次中断，一一对应
2. **收发不对称**：收包链长（中断→softirq→协议栈），发包链短（同步直发）
3. **`NET_RX` 是网络性能关键指标**：排查网络问题看 `NET_RX` 疯涨 = 收包压力大

## 数字差异说明

ping 200 个但中断涨 295，多出部分来自 ARP 解析、virtio 中断合并（interrupt coalescing）、背景包等。

## 汽车方向延伸

- 车载以太网（SOME/IP、DOIP）的**接收延迟**受 `NET_RX` softirq 调度影响 → 这正是 PREEMPT_RT 要把 softirq 线程化（ksoftirqd）的原因
- **发送路径**同步，延迟更可控

## 排查能力

能从 `/proc/interrupts` + `/proc/softirqs` 两个文件反推出一次网络包的完整中断旅程，即排查中断性能问题的核心能力。
