# 24 多核调度 SMP：per-CPU 队列、负载均衡与任务迁移

> 环境：内核 6.6.44（arm64，QEMU `-smp 4`，CFS/EEVDF，非 PREEMPT_RT）
> 主线：从单核 CFS 进入多核后，任务如何在 4 个核之间"分布与流动"。

---

## 0. 一句话总览

单核时代调度器只有一个全局队列；多核后每个核各有一个运行队列（per-CPU rq），
于是产生两个新问题，对应两个机制：

1. **任务该放哪个核？** → fork/wakeup 时的**主动选核**（`find_idlest_cpu`）
2. **跑起来后负载不均怎么办？** → 运行时的**被动搬运**（`load_balance`）

本文按"三课 + 两个实验"组织。

---

## 1. 第一课：多核架构与 per-CPU 运行队列

### 1.1 为什么每个核一个队列

单核只有一个 `struct rq`，所有 runnable 任务排在里面。多核若还用全局队列，
所有核抢一把锁，锁竞争会把并行优势吃光；且任务在核间"漂移"会破坏 cache 亲和性。

因此 Linux 选择 **per-CPU 运行队列**：每个 CPU 一个 `rq`，互不干扰。

### 1.2 源码：rq 是 per-CPU 变量

```c
// kernel/sched/core.c:118
DEFINE_PER_CPU_SHARED_ALIGNED(struct rq, runqueues);

// kernel/sched/sched.h:1210 声明 + 取值宏
DECLARE_PER_CPU_SHARED_ALIGNED(struct rq, runqueues);
#define cpu_rq(cpu)  (&per_cpu(runqueues, (cpu)))   // sched.h:1212
```

`struct rq` 定义在 `kernel/sched/sched.h:964`，CFS 专属的 `struct cfs_rq` 在
`sched.h:548`。`cpu_rq(cpu)` 是拿"某核运行队列"的标准姿势。

### 1.3 任务与核的绑定：`task_struct.cpu`

每个任务通过 `task_struct` 里的 `cpu` 字段记住自己在哪个核。用户态读
`/proc/PID/stat` **第 39 字段**（`processor`）就是它——本文实验全靠这个字段观测。

---

## 2. 两条分布路径（贯穿全文的对比）

| 路径 | 触发时机 | 源码入口 | 通俗说法 |
|------|---------|---------|---------|
| 主动选核 | fork / wakeup | `select_task_rq_fair` → `find_idlest_cpu` | 出生就分流 |
| 被动搬运 | 运行时负载不均 | `newidle_balance` → `load_balance` | 空闲核偷任务 |

---

## 3. 第二课：负载均衡 load_balance

### 3.1 fork 时的主动选核（先厘清"谁先动手"）

新任务第一次被唤醒走 `wake_up_new_task`：

```c
// kernel/sched/core.c:4848
void wake_up_new_task(struct task_struct *p)
{
    ...
    __set_task_cpu(p, select_task_rq(p, task_cpu(p), WF_FORK));  // core.c:4866
}
```

`select_task_rq`（`core.c:3626`）→ CFS 的 `select_task_rq_fair`（`fair.c:8045`）
→ 慢路径 `find_idlest_cpu`（`fair.c:7083`）：在调度域里挑"最空闲的核"放新任务。

**这就是实验 1 中 4 个 `yes` 依次落到核 3→2→1→0 的原因**：每个新任务 fork 时，
前一个已占了一个核，所以每次都挑到"当前最空闲"的那个。

### 3.2 运行时的被动搬运：newidle_balance

当某核 runqueue 空了、即将进 idle，`schedule()` 调 `newidle_balance`：

```c
// kernel/sched/fair.c:12182
static int newidle_balance(struct rq *this_rq, struct rq_flags *rf)
// "我这核要闲了，看看别处有没有任务能拉来跑"
```

它遍历调度域，对每个域调 `load_balance`（`fair.c:11165`）执行真正的搬运。

### 3.3 load_balance 三步走

```c
// kernel/sched/fair.c:11165
static int load_balance(int this_cpu, struct rq *this_rq,
                        struct sched_domain *sd, enum cpu_idle_type idle, ...)
```

```
① should_we_balance()    fair.c:11095  该我这个核负责平衡吗？（防多核重复搬）
② find_busiest_group()   fair.c:10739  找最忙的 CPU 组
③ find_busiest_queue()   fair.c:10880  找组内最忙的 runqueue
   → detach_tasks()      fair.c:8949   从忙核摘任务
   → attach_tasks()      fair.c:9111   挂到本核（dst_rq）
```

搬运工单是 `struct lb_env`（`fair.c:8678`）：`src_cpu/src_rq` = 忙核，`dst_cpu/dst_rq` = 发起核。

### 3.4 两条硬约束

1. **永远给源核留至少一个任务**：
   ```c
   if (busiest->nr_running > 1) { ... }   // fair.c:11165 附近
   ```
2. **单次搬运有上限**：
   ```c
   env.loop_max = min(sysctl_sched_nr_migrate, busiest->nr_running);
   ```
   `sysctl_sched_nr_migrate` 默认 32（`/proc/sys/kernel/sched_nr_migrate`）。

## 4. 第三课：调度域与任务迁移

### 4.1 谁能搬：can_migrate_task 四条拒绝规则

```c
// kernel/sched/fair.c:8813
/*
 * We do not migrate tasks that are:
 * 1) throttled_lb_pair, or
 * 2) cannot be migrated to this CPU due to cpus_ptr, or   ← 亲和性不符
 * 3) running (obviously), or                              ← 正在运行
 * 4) are cache-hot on their current CPU.                  ← cache 还热
 */
```

其中"正在运行"的显式判断：

```c
if (task_on_cpu(env->src_rq, p)) {   // p 正在源核上执行 → 不搬
    return 0;
}
```

### 4.2 怎么搬：detach_task 两步

```c
// kernel/sched/fair.c:8904
static void detach_task(struct task_struct *p, struct lb_env *env)
{
    deactivate_task(env->src_rq, p, DEQUEUE_NOCLOCK);  // ① 从源队列摘下
    set_task_cpu(p, env->dst_cpu);                      // ② 改 p->cpu
}
```

`set_task_cpu()` 改的就是 `task_struct.cpu` —— **`/proc/PID/stat` 第 39 字段变化的根源**。

### 4.3 正在运行的任务：migration_cpu_stop + [migration/N]

`load_balance` 只搬"排队中"的任务。正在跑的任务要强制迁移，靠 stop 线程：

```c
// kernel/sched/core.c:2575
static int migration_cpu_stop(void *data)
// 由每核一个的 stop 线程执行，优先级最高，能把目标核逼停后推任务
```

调用点之一：

```c
stop_one_cpu(task_cpu(p), migration_cpu_stop, &arg);   // core.c:5511
```

因此每个核都有一个 `[migration/N]` 内核线程（QEMU 里 `ps` 可见 `migration/0`~`migration/3`）。

### 4.4 调度域 sched_domain：平衡的范围

```c
// include/linux/sched/topology.h:87
struct sched_domain {
    struct sched_domain *parent;   // 上层域（更大范围）
    struct sched_domain *child;    // 下层域（更小范围）
    struct sched_group *groups;    // 域内调度组
    int flags;                     // SD_* 标志
    ...
};
```

层级：**MC**（同核兄弟）→ **DIE**（同封装）→ **NUMA**（跨节点）。QEMU virt 4 核通常只有
一个 DIE 域，故 4 核可自由互搬。

### 4.5 两条迁移路径对比

| | 负载均衡（被动） | 亲和性迁移（强制） |
|--|----------------|-------------------|
| 触发 | 负载不均，空闲核来偷 | `taskset`/`sched_setaffinity` 改 mask |
| 入口 | `load_balance` → `detach_tasks` | `set_cpus_allowed_ptr` → `migration_cpu_stop` |
| 搬谁 | 排队的 runnable 任务 | 任意任务（含正在跑的） |
| 执行者 | 发起方核自己 | stop 线程（最高优先级） |

## 5. 实验记录

### 实验 1：4 个任务无 pin，观察 fork 选核

```sh
cat /proc/cpuinfo | grep -c processor        # 确认 4 核
yes >/dev/null 2>&1 & P1=$!
yes >/dev/null 2>&1 & P2=$!
yes >/dev/null 2>&1 & P3=$!
yes >/dev/null 2>&1 & P4=$!
sleep 2
for p in $P1 $P2 $P3 $P4; do echo "PID=$p CPU=$(cut -d' ' -f39 /proc/$p/stat)"; done
kill $P1 $P2 $P3 $P4
```

输出（核号递减，对应 fork 顺序）：

```
PID=146 CPU=3
PID=147 CPU=2
PID=148 CPU=1
PID=149 CPU=0
```

**结论**：新任务 fork 时被 `find_idlest_cpu` 逐个放到空闲核，并非先堆一核再被搬走。

### 实验 2：pin 住 → 放开，隔离 load_balance

```sh
taskset -c 0 yes >/dev/null 2>&1 & P1=$!
taskset -c 0 yes >/dev/null 2>&1 & P2=$!
taskset -c 0 yes >/dev/null 2>&1 & P3=$!
taskset -c 0 yes >/dev/null 2>&1 & P4=$!
for p in $P1 $P2 $P3 $P4; do echo "PID=$p CPU=$(cut -d' ' -f39 /proc/$p/stat)"; done
# ↑ 4 个全 CPU=0（cpus_ptr={0} 锁死，can_migrate_task 规则 2 挡住）
taskset -pc 0-3 $P1; taskset -pc 0-3 $P2
taskset -pc 0-3 $P3; taskset -pc 0-3 $P4
sleep 2
for p in $P1 $P2 $P3 $P4; do echo "PID=$p CPU=$(cut -d' ' -f39 /proc/$p/stat)"; done
# ↑ 散开（load_balance 被动搬运）
kill $P1 $P2 $P3 $P4
```

pin 阶段输出（4 个全 0）：

```
PID=159 CPU=0
PID=160 CPU=0
PID=161 CPU=0
PID=162 CPU=0
```

放开后输出（散开，源核留一个）：

```
PID=159 CPU=2
PID=160 CPU=1
PID=161 CPU=3
PID=162 CPU=0
```

**结论**：放开后任务已"不新生"，fork 选核不再生效；散开完全由 `load_balance` 完成。
`162` 留下 = 源核至少留一个任务的约束。

## 7. 关键结论

1. 多核调度 = **per-CPU 运行队列**（并行 + 亲和）带来的"分布不均"问题，由**负载均衡**解决。
2. 任务分布有两条路径：**fork 主动选核**（`find_idlest_cpu`）与 **load_balance 被动搬运**。
3. `load_balance` 只搬"排队中"的任务，永远给源核留一个；正在跑的走 `migration_cpu_stop`。
4. 用户态通过 `/proc/PID/stat` 第 39 字段观测 `task_cpu`，是验证多核调度的最简手段。
