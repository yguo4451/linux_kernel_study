# 优先级反转实测：普通 mutex vs PI mutex

> 配套程序：`experiments/pi_demo/pi_demo.c`（arm64 静态编译，部署于 `/usr/bin/pi_demo`）

## 一、实验目的

用一段真实可跑的三线程程序，量化验证优先级继承（Priority Inheritance, PI）对实时系统的价值：

- 无 PI 时，高优先级任务会被一个"不相干"的中优先级任务间接阻塞
- 有 PI 时，锁持有者临时继承等锁者的优先级，快速释放锁

## 二、实验场景

三个线程全部 `sched_setaffinity` pin 到 CPU0（单核竞争），均为 `SCHED_FIFO`：

| 线程 | 优先级 | 行为 |
|------|--------|------|
| L（low） | 30 | 拿锁，进入 50ms 慢速临界区（`usleep` 模拟） |
| M（mid） | 50 | 忙等 300ms（抢占 L） |
| H（high） | 80 | 抢同一把锁，测量等待延迟 |

**两轮对比**：第一轮普通 `pthread_mutex`（无 PI），第二轮 `PTHREAD_PRIO_INHERIT` 属性（PI）。

## 三、运行结果

```
/usr/bin/pi_demo
=== 普通 mutex（无优先级继承）===
高优先级任务等待锁的延迟: 314 ms

=== PI mutex（优先级继承）===
高优先级任务等待锁的延迟: 40 ms

=== 对比 ===
无 PI: 314 ms
有 PI: 40 ms
差距: 274 ms   （约 7.8 倍）
```

## 四、时间线分析

### 无 PI（314ms）

```
t=0    L 拿锁，进入 50ms 临界区
t=10   H 阻塞在锁上（开始计时）
t=20   M 开始忙等 300ms
t=50   L 想释放 → 但 M(50) > L(30)，L 无法运行 ❌
t=320  M 忙等结束 → L 释放锁 → H 拿到锁
H 延迟 = 320 - 10 ≈ 314ms  ← 被 M 间接阻塞！
```

### 有 PI（40ms）

```
t=0    L 拿锁
t=10   H 阻塞 → L 继承 H 的优先级(80) ← PI 生效
t=20   M 开始忙等，但 L(已升到80) > M(50)
t=50   L 正常跑完临界区释放锁 → H 拿到锁
H 延迟 = 50 - 10 = 40ms  ← 只等 L 的剩余临界区
```

> 为什么 40 而不是 50？因为 H 在 L 拿锁 10ms 后才阻塞，L 临界区只剩 40ms。

## 五、程序关键点

```c
/* 第二轮：PI mutex */
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_setprotocol(&attr, PTHREAD_PRIO_INHERIT);  /* 关键一行 */
pthread_mutex_init(&lock, &attr);
```

```c
/* 顺序至关重要：H 必须先阻塞在锁上，M 再忙等抢占 L */
pthread_create(&tl, NULL, low_task, NULL);   /* ① L 先拿锁 */
usleep(10000);                                /* 等 L 拿到锁 */
pthread_create(&th, NULL, high_task, NULL);  /* ② H 抢锁 → 阻塞 */
usleep(10000);                                /* 等 H 阻塞在锁上 */
pthread_create(&tm, NULL, mid_task, NULL);   /* ③ M 忙等 → 抢占 L */
```

## 六、内核机制：优先级继承

用户态 `PTHREAD_PRIO_INHERIT` 的 mutex 最终落到内核的 **rt_mutex**（`kernel/locking/rtmutex.c`）：

1. H 在 futex 上等锁时，内核走 `futex_lock_pi()` → `rt_mutex_lock()`
2. rt_mutex 发现锁被 L 持有 → 调用 `rt_mutex_adjust_prio()`（rtmutex.c:504 附近）
3. L 的 `pi_top_task` 指针被设为 H，L 的动态优先级被临时提升到 H 的 80
4. L 释放锁后优先级回落到 30

观测方式：`/proc/<L的tid>/stat` 第 18 字段 = `task->prio - 100`（源码 `fs/proc/array.c`：
`priority = task->prio - MAX_RT_PRIO`，MAX_RT_PRIO=100）。boost 时该字段从 **-31**（FIFO 30 → 69-100）
跳到 **-81**（FIFO 80 → 19-100）。

配套采样工具 `watch_prio`（`experiments/pi_demo/watch_prio.c`，部署 `/usr/bin/watch_prio`），
连续打印第 18 字段。观测步骤（先关节流）：

```sh
echo -1 > /proc/sys/kernel/sched_rt_runtime_us   # 禁用 RT throttling
HOLD_MS=5000 MID_MS=8000 /usr/bin/pi_demo &      # 第一轮打印 [L] tid=A，第二轮 [L] tid=B
watch_prio A 100    # 第一轮：恒 -31（无 boost）
watch_prio B 100    # 第二轮：-31 → -81 跳变（boost 生效）

# 更从容的观测：跳过第一轮 + 推迟 boost 3 秒，给观察者准备时间
SKIP_NO_PI=1 HOLD_MS=5000 MID_MS=8000 PREP_MS=3000 /usr/bin/pi_demo &
watch_prio <L的tid> 100   # 先看到 -81（boost 中）→ -31（释放回落）
```

实测数据（关节流后）：

| 轮次 | 配置 | H 延迟 | L 的 prio 观测 |
|------|------|--------|---------------|
| 无 PI | HOLD_MS=5000 MID_MS=8000 | 8011ms（被 M 阻塞 8s） | 恒 -31 |
| 有 PI | 同上 | 4991ms（L 按时释放 5s） | -31 → -81 跳变 |
| 有 PI（PI-only + PREP_MS） | SKIP_NO_PI=1 PREP_MS=3000 | 1993ms（5000-3000） | 采样到 -81 → -31 回落 |

`-81` = L 被 boost 到 FIFO 80（99-80-100），`-31` = L 正常 FIFO 30（99-30-100）。
`-81 → -31`（回落）与 `-31 → -81`（跳升）等价，都是 PI 生效的直接证据。

## 七、踩坑记录

| 问题 | 现象 | 根因 | 修复 |
|------|------|------|------|
| 无 PI 测到 0ms | H 拿锁时 L 早释放了 | H 创建在 M **之后**，主线程(SCHED_NORMAL)被 M 饿死，H 创建太晚 | H 先阻塞、M 再忙等 |
| `sched: RT throttling activated` | PI 轮延迟异常 | M 忙等 500ms×2 轮=1000ms 超 RT 预算 950ms/1s | M 忙等降为 300ms（2×300=600ms < 950ms） |
| 反转"没发生" | 两轮延迟相同（都≈5000ms） | 观测时 HOLD_MS 调到 5000 却让 MID_MS=3000，M 比 L 临界区先结束 | MID_MS 必须 > HOLD_MS，M 才能一直抢占到 L 释放时刻 |

**教训**：
1. 线程创建顺序就是实验设计本身——H 必须先阻塞、M 再忙等，否则主线程被 M 饿死。
2. RT 任务忙等消耗 RT 带宽，超 `sched_rt_runtime_us`（默认 950ms/1s）会触发节流，可 `echo -1` 关闭。
3. 反转的必要条件是 **M 忙等时间 > L 临界区时间**；若 M 先结束，反转不会发生。

## 八、线程级还是进程级？

**优先级反转是线程级的，不是进程级的。**

Linux 内核调度单元统一是 `task_struct`（一个 task = 一个线程），优先级字段挂在每个 task 上：

```c
struct task_struct {
    int prio;            /* 动态优先级（含 PI boost）*/
    int static_prio;     /* 静态优先级（nice）*/
    unsigned int rt_priority;  /* 实时优先级 */
};
```

"进程"只是共享同一 mm/tgid 的一组线程（线程组），调度器 `schedule()` 只看 task，不关心进程边界。rt_mutex 的 `owner` 也是 `struct task_struct *`（线程）。

**实验即铁证**：本实验的 L/M/H 是同一进程 `pi_demo` 的三个线程（FIFO 30/50/80），反转照样发生——反转不需要跨进程。

术语上，教材常说"进程优先级反转"是历史遗留（传统单线程 OS 进程=任务）；Linux 下应精确说"任务/线程优先级反转"，POSIX 的 `PTHREAD_PRIO_INHERIT` 也是线程属性。

## 九、汽车相关性

优先级反转是车载实时系统（如 AUTOSAR OS、ECU 之间共享资源）的经典事故源。1997 年火星探路者号就因优先级反转（气象任务 M 阻塞高优先级总线任务 H）反复重启。车载场景里，低优先级诊断任务持有 CAN 总线锁、被中优先级任务抢占，可能让高优先级刹车控制任务错过死线——这正是 `PTHREAD_PRIO_INHERIT`（或 PREEMPT_RT 的 rt_mutex）必须存在的理由。
